Cloudflare / private integration

Connect real monitoring.

Install a small adapter in the private API project and deploy a separate read-only snapshot Worker. This docs site never needs the API source or any Cloudflare secret.

Owner setup required

Until the API adapter and Worker are deployed and configured, Usage shows no invented totals and Status labels catalog entries as historical only.

What this collects

Normalized route template, method, HTTP status, time to response headers, and whether the request came from the scheduled monitor. It does not store request or response bodies, query values, headers, tokens, IP addresses, email addresses or dynamic resource IDs.

Normal traffic counts include bots and other clients; this is not a count of people. Recent events are sampled observations, not a complete audit log. Cloudflare Analytics Engine provides weighted sampling-aware estimates.

Automatic checks use a reviewed, fixed set of read-only health, search and metadata routes. Generation, downloads, uploads, builds and mailbox creation are not triggered. All other routes are marked passive: their health is inferred only from real observed traffic.

1. Keep the API repository private

Do not upload or copy the private API repository into this docs project. In the private API project, copy only these two generic files from this repository: cloudflare/adapter.mjs and cloudflare/routes.mjs into a private path such as src/observability/. The route file is generated from the fixed public contract list; it is not discovered from the health response.

Add the Analytics Engine dataset binding from cloudflare/api-binding.example.toml to the private project's existing Wrangler configuration. Merge the binding only; preserve the current main entry, bindings, settings and scheduled triggers.

Wrap the existing exported module with withObservability(existingWorker) as shown in cloudflare/entrypoint.example.mjs. Adjust the import path to the real handler. Keep its fetch handler, response object, streaming, cron jobs and other exports. The wrapper returns the original response and fails open if telemetry cannot be written.

import existingWorker from './existing-worker.mjs';
import {withObservability} from './observability/adapter.mjs';
export default withObservability(existingWorker);

Deploy the private API update using its existing workflow. Validate one ordinary safe API request and one monitor request. The monitor token header is stripped before the existing application handler runs.

2. Create the dedicated monitoring database

In Cloudflare, create a new D1 database named lodearink-observability. Do not reuse the API's application database. Put the new ID in cloudflare/wrangler.toml; this file is a template for a separate Worker and must not replace the API configuration.

From this repository's cloudflare/ directory, apply the schema and the generated reviewed probe queue:

npx wrangler@4 d1 execute lodearink-observability --remote --file=schema.sql
npx wrangler@4 d1 execute lodearink-observability --remote --file=seed.sql

The bounded D1 schema stores at most twelve monitoring outcomes per route and one shared prepared snapshot. It does not store per-request records. Re-running the seed file is safe.

3. Store narrowly scoped secrets in Cloudflare

Create a custom Cloudflare token with only Account → Account Analytics → Read permission. In the monitoring Worker's directory, set it as a Worker secret. It is used only by the scheduled snapshot job for the Analytics Engine SQL API.

npx wrangler@4 secret put CF_ANALYTICS_TOKEN

Generate a separate random value with at least 32 bytes of entropy. Set the exact same value as a secret on both the monitoring Worker and the private API Worker:

openssl rand -hex 32
npx wrangler@4 secret put MONITOR_TOKEN

Paste the generated value only into Cloudflare's hidden secret prompts in each project. In the companion Worker, run npx wrangler@4 secret put MONITOR_TOKEN. In the private API project, run the same command there and enter the same generated value. Never put it in this site, a source file, command argument, Git, an issue, or chat. The API Worker uses it to flag and exclude scheduled monitor traffic from normal usage totals.

4. Configure and deploy the snapshot Worker

In cloudflare/wrangler.toml, set your Cloudflare account ID, the D1 database ID, API origin and the docs origin. Use https://lodearink-docs-o4dd.vercel.app for the current docs origin. Configure the existing API origin exactly; both are public hostnames, not secrets.

From the cloudflare/ directory, add the Worker secrets, then publish the separate companion Worker:

npx wrangler@4 secret put MONITOR_TOKEN
npx wrangler@4 deploy

The one-minute schedule shares a single D1 snapshot and advances at most four due endpoint checks per run, with at most two checks in flight. Each route is checked about every two hours. A snapshot performs three fixed Analytics Engine reads, below the free-plan query allowance, and checks never follow redirects or run generation, uploads, downloads or account creation.

Each dashboard refresh makes one indexed D1 snapshot-row read. The browser does not query Analytics Engine; those three reads happen only once in the shared minute schedule. Cloudflare Cache API behavior is not assumed on workers.dev.

Read Cloudflare's account-wide free limits before enabling this on a busy account. Current documented Free allowances are 100,000 Workers requests/day, 10 ms CPU and 50 outgoing subrequests/invocation; Analytics Engine allows 100,000 data points and 10,000 SQL reads/day; D1 allows 5 million rows read, 100,000 rows written per day and 5 GB total storage. These limits are shared with the rest of your Cloudflare account. The schedule makes 4,320 Analytics Engine queries/day at three reads per minute, before retries or other account use. Each dashboard refresh performs one indexed D1 row read. This design is bounded but cannot guarantee staying within account limits when existing traffic is already near quota.

5. Point the docs site at the public snapshot

After the Worker is deployed, copy its public workers.dev URL and append /v1/snapshot. Set only snapshotUrl in data/observability-config.json. It must be a public HTTPS URL; never put a token or account ID there.

{
  "snapshotUrl": "https://YOUR-WORKER.YOUR-ACCOUNT.workers.dev/v1/snapshot"
}

Build and deploy the docs site using its existing Vercel setup. The browser reads the shared public snapshot once a minute, never triggers checks and never receives the Analytics Engine token.

6. Verify real traffic and safe checks

In this documentation repository, the adapter, sampling, public snapshot and bounded scheduler tests use in-memory mocks and do not contact the private API or Cloudflare:

npm run build
npm test
node --test tests/cloudflare*.test.js tests/observability-client.test.js

With the documentation workflow running on port 5000, run node tests/observability-browser.mjs for a responsive browser check. It injects a clearly isolated test snapshot, intercepts the mock Worker URL and makes no calls to Cloudflare or the API.

For local Worker route checks, from cloudflare/ run npx wrangler@4 dev. In another terminal, try curl -i http://127.0.0.1:8787/v1/snapshot, the same request with -H 'Origin: https://lodearink-docs-o4dd.vercel.app', and a POST request that should return 405. Without a seeded local D1 snapshot, 503 with awaiting-first-scheduled-snapshot is expected. Do not put local secrets in a tracked file; cloudflare/.dev.vars is gitignored.

  1. Send one ordinary read-only request to the private API after deploying the adapter.
  2. Wait for the next scheduled snapshot, then open Usage and check that the normalized endpoint, method and HTTP status appear without request content.
  3. Check Status for the next scheduled check, its result and the passive-only coverage count.
  4. In Cloudflare, check that Analytics Engine has new points in lodearink_requests, D1 has one snapshot row and that a monitor request appears with source monitor, not as normal usage.
  5. If no live snapshot appears, verify the D1 ID, dataset binding name, both matching secrets, docs origin allowlist, Analytics permission and scheduled Worker events. Dashboard failure never changes a private API response.

Free-plan and retention notes

The public snapshot is aggregated; sampled individual events cannot reconstruct exact request order. Analytics Engine retains its own data for a limited period. D1 stores only one prepared usage snapshot and a twelve-result ring per monitored route; monitoring history therefore spans the recent scheduled-check sample window, not a permanent archive.

Active availability counts successful responses versus confirmed HTTP/application failures. Timeouts, authentication issues, validation responses and redirects are excluded from the availability percentage rather than called downtime. Passive observations are shown separately and are never labeled as active uptime.
